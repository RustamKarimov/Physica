# Step 15 — Math Editor and Semantic Equation Tree Implementation Specification

**Status:** IMPLEMENTATION-READY

**Owning roadmap item:** Phase 4, Step 4.1 — Math editor + semantic equation tree

**Primary owner:** `@physica/equations`

## 1. Purpose and source audit

Step 15 establishes editable mathematical content as persistent semantic data. A teacher edits LaTeX through MathLive, Physica parses it into canonical MathJSON, assigns stable Physica-owned semantic node identities, and renders final presentation markup with KaTeX. The editable source, canonical meaning and rendered glyphs remain distinct layers.

The design was audited against the Project Constitution, ADR-015, Package Dependencies, Equation Engine, Mathematics and Units, Text Content, Typography and Internationalization, the frozen architecture blueprint, HC-01 and the Example Gallery contract. It requires no Architecture Blocker, ADR, root `ProjectDocument` schema change, new workspace package, clock, solver, scheduler phase or authoritative runtime writer.

The existing generic `EquationDefinition` envelope is sufficient. Step 15 defines one namespaced configuration inside that envelope instead of changing the project schema.

## 2. Ownership and scope

`@physica/equations` owns the V1 equation model, canonical MathJSON conversion, semantic identity tree, edit reconciliation, validation, conversion to and from the existing project envelope, and stable KaTeX rendering contract. It depends only on the public `@physica/core-model` API plus the pinned Compute Engine and KaTeX libraries. It does not depend on React, MathLive, editor internals, render backends, physics domains, clocks or runtime state.

`@physica/desktop` owns the MathLive web-component adapter and the Step 15 interactive proof. MathLive is an input surface only. The desktop always submits its LaTeX value through the public equations package and never accepts renderer output as identity or persisted meaning.

Step 15 includes:

- editable LaTeX source with MathLive keyboard and accessibility behavior;
- canonical MathJSON parsing through the Compute Engine;
- a JSON-safe semantic tree with stable UUID-v4 node IDs;
- edit reconciliation that preserves IDs for unchanged semantic subtrees;
- typed validation and parse diagnostics;
- conversion to and from `EquationDefinition` using type ID `physica:equation/model-v1` and schema version 1;
- stable KaTeX HTML/MathML rendering with untrusted capabilities disabled;
- the `examples/equations/edit-and-render` gallery example;
- a launcher-visible equation workbench.

Step 15 does not implement equation-transform matching, source-to-target correspondence maps, equivalence proofs, step validation, handwritten recognition, graphing, live variable binding, equation animation, custom notation registries, unit inference, CAS evaluation UI or text-block embedding. Those remain later roadmap work.

## 3. Persisted equation model

`EquationModelV1` contains:

- the existing stable `EquationId`;
- a non-empty teacher-facing name;
- `source` with `kind: "latex"` and the exact edited LaTeX string;
- `canonicalMathJson` as finite JSON data produced by the pinned Compute Engine;
- `semanticRoot` as the Physica identity layer mirroring the canonical JSON structure;
- parse status and JSON-safe diagnostics;
- optional JSON-safe metadata.

The generic project envelope uses `typeId: "physica:equation/model-v1"`, `schemaVersion: 1` and stores only the model configuration. Envelope enabled state remains envelope-owned. Parsing rejects other type IDs or schema versions with typed errors and does not reinterpret unknown plugin data.

The canonical expression is persisted so saved projects are not silently reinterpreted by a future library upgrade. Loading validates that the identity tree mirrors the persisted canonical JSON; it does not recanonicalize source as a side effect. Explicit editing is the only operation that replaces canonical content.

## 4. Semantic identity tree

`SemanticEquationNode` is a JSON-safe recursive union that represents canonical MathJSON without using TeX tokens or glyph spans as identity:

- `atom` stores a JSON primitive;
- `list` stores ordered child nodes and represents MathJSON arrays;
- `record` stores lexicographically ordered named child nodes and represents MathJSON dictionaries.

Every node owns a UUID-v4 `SemanticEquationNodeId`. IDs are generated by an injected `SemanticEquationIdFactory`; production uses `crypto.randomUUID()` and tests/examples use a deterministic factory. Duplicate or malformed IDs are invalid.

Each node carries a deterministic structural fingerprint derived from kind, value, ordered list children or ordered record keys. The fingerprint is diagnostic/matching data, never the persistent identity itself.

## 5. Editing and identity reconciliation

Creating an equation parses source, canonicalizes it, constructs an identity tree and freezes the result. Editing performs the same parse and then reconciles the new semantic tree against the previous tree.

Reconciliation indexes every previous node by exact structural fingerprint and consumes candidates in previous-tree traversal order. An unchanged subtree keeps its previous root ID; unchanged descendant subtrees also keep their IDs when an ancestor changes or the subtree moves. Newly introduced or semantically changed nodes receive new IDs. Each previous ID can be reused at most once, so repeated identical symbols remain distinct and deterministic.

Reconciliation compares semantics, not source spelling, DOM ranges, KaTeX spans or MathLive offsets. Canonically equivalent spelling may therefore retain identity when canonical MathJSON is unchanged. Identity is never regenerated merely because rendering or canonical serialization runs again.

## 6. Parsing, validation and errors

The Compute Engine parses LaTeX in canonical mode. A valid edit must have non-empty source, produce finite JSON-safe MathJSON, and report a valid canonical expression. Invalid source returns a typed `EquationResult` error and leaves the caller’s prior model untouched.

Stable public error kinds cover invalid name/source, parse failure, non-JSON canonical output, invalid semantic node, invalid or duplicate semantic ID, semantic/canonical mismatch, invalid metadata, unsupported envelope type/version and rendering failure. Expected teacher input failures are results rather than thrown developer exceptions.

Validation recursively enforces finite JSON primitives, sorted unique record keys, exact identity-tree/canonical-tree shape, UUID-v4 IDs, unique IDs, immutable canonical data and JSON-safe diagnostics/metadata. Public successful values are deeply frozen.

## 7. Canonicalization and version policy

`@cortex-js/compute-engine` is pinned exactly at 0.120.0 under the MIT license. Physica stores the canonical MathJSON and records the canonicalizer identifier/version in the model, because canonical forms are stable within a library version but may change across versions.

Canonicalization is editor-independent. The equations package invokes the Compute Engine directly rather than accepting MathLive’s internal expression object. Custom notation dictionaries are not added in Step 15; unsupported or invalid semantic input returns diagnostics instead of being guessed.

Changing the canonicalizer version later requires compatibility tests and an explicit migration or reparse command. Project load never performs an implicit upgrade.

## 8. Input and rendering security

MathLive is pinned exactly at 0.110.0 under the MIT license. Versions through 0.109.2 are forbidden because of CVE-2026-54705; 0.110.0 is the first patched release. The desktop reads `MathfieldElement.value` on the `input` event and sends plain LaTeX to `@physica/equations`. It does not use MathLive static HTML conversion or inject MathLive-produced markup.

KaTeX is pinned exactly at 0.18.4 under the MIT license. `renderEquationToMarkup` uses `renderToString` with display-mode selection, `throwOnError: true`, `trust: false`, strict error handling and no caller-provided macros. Render output is presentation-only and cannot feed semantic IDs or canonical content.

The desktop may insert only markup returned by this locked renderer configuration. Raw source and diagnostics are rendered as text. Tests include hostile text/URL-like source and assert that trusted HTML capabilities are rejected or escaped.

## 9. Serialization and separation

`toEquationDefinition` and `parseEquationDefinition` bridge the domain model to the existing core envelope. Canonical project serialization already preserves its JSON-safe configuration; Step 15 adds round-trip tests proving source, canonical MathJSON, semantic IDs, diagnostics and metadata survive exactly.

The model is document state. Compute Engine objects, MathLive elements, DOM nodes, KaTeX markup caches, selections and editor focus are transient and never serialized. No runtime state store, physics channel, clock or solver is read or written.

## 10. Performance and accessibility

Parsing cost belongs to an explicit edit. Reconciliation and validation are linear in semantic tree size apart from fingerprint string construction. The desktop updates immediately for the foundation example; worker/debounce infrastructure is deferred until profiling establishes a need.

The MathLive field has a visible label and accessible description. Canonical status, parse errors and identity counts are textual. The final KaTeX output includes MathML/ARIA content. Keyboard editing is first-class, focus is visible, color is not the only status signal and the proof remains useful without animation.

## 11. Test matrix

Tests cover:

- valid scalar, symbolic, relation, fraction and function parsing;
- canonical MathJSON determinism at the pinned version;
- exact identity-tree mirroring and deep immutability;
- deterministic IDs from the injected factory;
- preservation of unchanged whole trees, moved subtrees and unchanged descendants;
- new IDs for changed nodes and one-time reuse for duplicate subtrees;
- empty/invalid source, invalid MathJSON and malformed persisted trees;
- duplicate/non-UUID semantic IDs, unsorted record keys and semantic mismatch;
- envelope type/version/configuration validation and exact round trip;
- canonical serialization round trip through the existing serialization package;
- deterministic KaTeX output and rejection/escaping of untrusted capabilities;
- example metadata, accessible preview and expected-output determinism;
- desktop typecheck/build with the MathLive input adapter.

No numerical/scientific reference model is required because Step 15 represents mathematics but does not evaluate a physical model or claim equivalence. Tests do assert known canonical structures to prevent semantic drift.

It replaces the prior Step 14 showcase as the current launcher-visible proof; the Step 14 gallery example and tests remain intact. `Launch Physica.bat` remains the one-click launcher; no executable packaging is added.
